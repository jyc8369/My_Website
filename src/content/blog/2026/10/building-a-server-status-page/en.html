Why I Built a Status Page

On October 18, 2026, I built and deployed status.jyc8369.dev, a small service for checking the health of several Linux servers in one place. It displays CPU usage and operating-system uptime and indicates whether each server is responding to status requests.

A Lightweight API for Linux Server Metrics

I started by building a lightweight backend API in Rust. It returns host-wide CPU usage, operating-system uptime, and the collection timestamp as JSON. CPU usage is sampled once per second in the background, and a separate health-check endpoint is available.

I only needed a few metrics for this project. Instead of building a complex monitoring platform, I focused on a small API that reports the information the page actually uses.

Reaching Multiple Nodes Through One Cloudflare Tunnel

Rather than installing Cloudflare Tunnel on every server, I configured one tunnel on a proxy server. That proxy can reach the other devices over a private Tailscale network. Status requests from the Cloudflare side travel through this route to reach each server's API.

The main benefit is that I can query several devices through a single entry point without managing a separate tunnel on each node.

A Status Dashboard on Cloudflare Pages

I deployed the user-facing interface to Cloudflare Pages. The static page uses Pages Functions to retrieve JSON status reports and display them in the dashboard. The current frontend refreshes every 30 seconds, updating CPU usage, uptime, and whether each device responded.

Because this page only needs periodic checks, I do not need to stream every metric with minimal latency.

What This Simpler Design Trades Off

Using one proxy makes the setup easier to manage, but it also concentrates requests on a single path. If the proxy or the network route fails, the dashboard may show servers as unavailable even when those servers are still running. Additional hops can also affect response time.

That makes the design a poor default for workloads that require extremely low latency or immediate fault detection. For my goal of checking basic server health at intervals, simpler operations are the priority for now.

Open Source and Next Steps

I published both projects on GitHub: the status page and the backend API server.
