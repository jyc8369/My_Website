상태 페이지를 만든 이유

2026년 10월 18일, status.jyc8369.dev를 개발하고 배포했습니다. 여러 Linux 서버의 상태를 한곳에서 확인하기 위한 작은 서비스입니다. 각 서버의 CPU 사용률과 운영체제 업타임을 표시하고, 서버가 요청에 정상적으로 응답하는지도 확인할 수 있도록 만들었습니다.

Linux 서버의 상태를 제공하는 API

먼저 Rust로 경량 백엔드 API를 작성했습니다. 이 API는 서버 전체의 CPU 사용률과 업타임, 측정 시각을 JSON으로 반환합니다. CPU 사용률은 백그라운드에서 1초 간격으로 수집하며, 별도의 헬스 체크 엔드포인트도 제공합니다.

이번 프로젝트에 필요한 정보는 많지 않았습니다. 복잡한 모니터링 시스템보다 필요한 지표를 안정적으로 전달하는 단순한 API에 집중했습니다.

하나의 Cloudflare Tunnel로 여러 노드 연결하기

네트워크 구성에서는 각 서버에 Cloudflare Tunnel을 설치하는 대신 프록시 서버 한 대에 터널을 구성했습니다. 이 프록시 서버는 Tailscale 사설망을 통해 다른 장치에 접근합니다. Cloudflare 측의 상태 조회 요청은 이 경로를 거쳐 각 서버의 API에 전달됩니다.

이렇게 하면 개별 서버 노드마다 터널을 별도로 관리하지 않아도 됩니다. 여러 장치를 하나의 진입 경로로 조회할 수 있다는 점이 이번 구성의 핵심입니다.

Cloudflare Pages에 배포한 상태 화면

사용자가 보는 화면은 Cloudflare Pages에 배포했습니다. 정적 페이지와 Pages Functions를 연결하여 서버가 제공하는 JSON 응답을 상태 화면에 표시하도록 구성했습니다. 현재 프런트엔드는 30초마다 상태를 다시 조회하며, CPU 사용률과 업타임, 응답 가능 여부를 갱신합니다.

단순히 서버가 응답하는지 주기적으로 확인하는 목적이므로, 모든 지표를 초저지연으로 전송할 필요는 없다고 판단했습니다.

단순한 구조의 장점과 한계

단일 프록시를 사용하는 방식은 설정과 관리가 간단하지만, 조회 경로가 하나로 모인다는 한계가 있습니다. 프록시나 네트워크 경로에 장애가 생기면 실제 서버가 정상적으로 동작하더라도 상태 페이지에서는 응답 불가로 표시될 수 있습니다. 중간 경로가 늘어나는 만큼 응답 지연에도 영향을 받을 수 있습니다.

따라서 매우 낮은 지연 시간이 필요하거나 즉각적인 장애 감지가 중요한 서비스에 이 구성을 그대로 적용하기는 어렵습니다. 제 목적은 서버 상태를 일정 간격으로 확인하는 간단한 페이지이기 때문에, 현재는 운영의 단순함을 우선했습니다.

오픈 소스 공개와 앞으로의 계획

이번에도 코드를 GitHub에 공개했습니다. 상태 페이지 소스 코드와 백엔드 API 서버 소스 코드를 각각 확인할 수 있습니다.

다만 프록시의 상세 구성과 내부 요청 경로, 보안 관련 설정은 현재 글에 포함하지 않았습니다. 전체 흐름과 보안 구성을 충분히 검토한 뒤 공개해도 안전하다고 판단되는 범위에서 설명을 보완할 예정입니다. 그때 이 글도 함께 수정하겠습니다.
